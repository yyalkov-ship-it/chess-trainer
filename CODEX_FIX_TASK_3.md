Stage 4 принят. Мой независимый прогон (python-chess + Stockfish 18, Threads 4, Hash 512,
depth 20) по обеим партиям дал **0 замечаний**, CI на `e6b3936` зелёный, живой сайт отдаёт тот же

Ниже три хвоста. Ни один не мешает пользоваться приложением, но первый — настоящая мина.

## 1. Прибить версию движка в CI (главное)

Билд `b562037` упал на `упражнение 3: отрыв 0.89 < 1.50` (`Bxd7+`). Позиция при этом была
корректная:

| Движок | Отрыв `Bxd7+` |
|---|---|
| Stockfish 18, Hash 512 (моя проверка) | 2.34 |
| Stockfish 18, Hash 256 (твой локальный прогон) | 1.83 |
| Stockfish 16 из apt (CI) | 0.89 |

`sudo apt-get install -y stockfish` на `ubuntu-latest` ставит **Stockfish 16**, а пороги 1.5
калиброваны на Stockfish 18. Проверяющий движок обязан совпадать с калибровочным, иначе новый
контент будет случайно краснеть или, что хуже, случайно проходить.

Замена задачи на `Bf5+` красноту убрала, но причину — нет. Запас всё ещё тонкий: упражнение
`Nf5` на SF16 даёт отрыв **1.90** при пороге 1.50.

Что сделать:

- убрать `apt-get install stockfish` из `.github/workflows/deploy-pages.yml`;
- ставить **официальный Stockfish 18** (релизный бинарник с GitHub,
  `stockfish-ubuntu-x86-64-avx2`) и передавать путь через `STOCKFISH_PATH`;
- если бинарник недоступен — падать с явной ошибкой, а не молча уходить на другую сборку;
- в начале `verify:engine` печатать первую строку баннера движка (`Stockfish NN by ...`),
  чтобы версия была видна в логе CI.

Альтернатива, если не хочется возиться с бинарником: не ставить системный stockfish вообще и
дать `engine-node.ts` уйти на встроенный `node_modules/stockfish/bin/stockfish-18.js`. Версия
совпадёт точно, ценой более долгого прогона.

## 2. Разобрать второй ответ чёрных в задаче `Bf5+`

Позиция: `1r4r1/pbpknp1p/1b3P2/8/8/B1PB1q2/P4PPP/3R2K1 w - - 0 22`.

В объяснении разобран только `22.Bf5+ Ke8 23.Bd7+ Kf8 24.Bxe7#`. Но у чёрных **два** легальных
ответа: `Ke8` и `Kc6`. Ребёнок, отыгрывая позицию за чёрных, легко уйдёт в неописанную ветку и
не найдёт своё продолжение в тексте.

Добавь в объяснение вторую ветку — с реальным вариантом, посчитанным движком, а не по памяти.

## 3. Защита от терминальной позиции в ветке опровержений

`scripts/verify-with-engine.ts`: в цикле по `moment.refutations` результат разыменовывается
напрямую —

```ts
const analysis = await engine.analyse(wrong.fen(), 3)
const loss = (correctEval + analysis[0].cp) / 100
```

— без той проверки на мат/пат, которая есть в `evaluatePosition`. Если опровержение когда-нибудь
окажется матующим или патующим ходом, `analysis` придёт пустым и скрипт упадёт с невнятной
ошибкой вместо осмысленного сообщения.

Вынеси общую логику: терминальную позицию оценивать без обращения к движку, непустоту `analysis`
проверять явно.

## Критерии приёмки

1. `.github/workflows/deploy-pages.yml` использует Stockfish 18, версия видна в логе прогона.
2. Объяснение к `Bf5+` покрывает обе защиты чёрных, вариант посчитан движком.
3. `verify-with-engine.ts` не падает на терминальной позиции в ветке опровержений; добавь
   короткий тест или искусственную проверку, подтверждающую это.
4. `npm run validate:content`, `npm run verify:engine`, `npm run build` проходят локально.
5. CI зелёный, деплой прошёл, живой сайт отдаёт тот же бандл, что собирается локально.
6. В журнале проекта записано, какой версией движка проверяется контент и почему это важно.
